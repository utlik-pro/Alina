## Первый набор изменений

- Instagram отправляет ответы через свой канал без зависимости от наличия Wappi.
- Явный отказ или перенос решения («No thanks», «Don't book», «I will confirm later») завершает ход до вызова модели и инструментов бронирования.
- Смена массажа лица на массаж тела обновляет услугу и сбрасывает длительность предыдущей услуги, сохраняя контакт.

- Реплеи проходят через обработчик канала с подменёнными внешними сервисами; включают отказ и последующее возвращение клиента.

## Второй набор изменений: повторные записи и сверка

Добавлена таблица `booking_attempts`. Стандартный запуск `Database.create_tables()` создаёт её автоматически; существующие таблицы не изменяются. Production-база в ходе разработки не затрагивалась.

Перед созданием записи процесс атомарно сохраняет ключ (клиент, нормализованное название услуги, дата/время). Только один процесс может получить этот ключ. После ошибки, тайм-аута или перезапуска повторная попытка с тем же ключом блокируется. Отметка не истекает автоматически: сначала требуется сверка. Разные написания названия услуги пока не сведены к единому каталожному ID; это ограничение защиты.

В комментарий YClients добавляется `[operation:…]` для поиска записи, если ответ сервера потерян. Подтверждение требует непустого ID записи. Успешная попытка хранит ID YClients; неопределённая остаётся pending. Новая запись на то же время после отмены также требует ручного разбора ключа — автоматического удаления защиты нет.

Отчёт сверки (только чтение, использует DATABASE_URL и ключи YClients выбранного окружения):

```sh
cd /Users/admin/Alina/.worktrees/crystal-v2/massage-booking-bot
PYTHONPATH=. python3.11 scripts/reconcile_booking_attempts.py --limit 100
```

Отчёт проверяет ID, дату/время, длительность и признак удаления. Он не утверждает полное совпадение услуги, контакта или оплаты. При отсутствии ID требуется поиск маркера операции; недоступность API не трактуется как отсутствие записи. Команда ничего не создаёт, не переносит и не подтверждает автоматически. На production она не запускалась.

Если позже потребуется откат к старому коду, новую таблицу можно оставить: старый код её не использует. При этом старая версия не имеет защиты от неопределённых попыток v2 — перед переключением нужно разобрать pending-записи.

## Третий набор изменений: память диалога, перенос и отмена

- `conversation_snapshots` сохраняет выбранную услугу, дату/время, контакт, отказ и последние сообщения перед отправкой ответа. При первом ходе после рестарта снимок загружается из базы. Слоты и признак текущего подтверждения YClients не восстанавливаются из кэша.
- Reset удаляет сохранённый снимок. Закрытые диалоги и клиенты вне зоны обслуживания не включаются в список потерянных клиентов DialogManager.
- При недоступности хранилища бот сообщает техническую ошибку, а не начинает продажи с пустым контекстом.
- Перенос изменяет локальные записи только после положительного ответа YClients. Ошибка проверки доступности останавливает перенос.
- Отмена изменяет локальный статус и применяет штраф/списание только после подтверждения календаря. Отказ API не освобождает слот для листа ожидания.
- Ответы после операций различают успешное изменение и ожидающий проверки запрос. Instagram получает эти ответы независимо от Wappi.
- Сверка ищет точную метку операции, если ID ответа потерялся. Единственное найденное совпадение проверяется по расписанию; отчёт не меняет базу. Неполный ответ (100 записей) или сбой поиска дают `unverified`.

### Проверка перед живым использованием

Тесты используют временные SQLite-базы и подмену внешних API. Проверены рестарт, отказ API, успешная операция, потерянный ответ, ограниченная выборка и отказ хранилища.

Для живого прогона ещё нужны определённый владельцем тестовый канал и тестовый календарь. Продакшен-каналы не переключались. Внешние автоответчики ManyChat нужно проверить именно на этом канале: локальные тесты не видят их настройки.

Границы реализации: сохранение диалогов рассчитано на существующую обработку последовательных ходов одного клиента; распределённая блокировка диалога между несколькими репликами не добавлялась. Сбой локальной БД после успешного изменения календаря требует ручной сверки. Снимки и таблица попыток не заменяют резервную копию базы.
